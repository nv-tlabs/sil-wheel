# Search-Tool Calibration — How Noisy Is Each Tool, Really?

**Audience**: anyone (human or agent) deciding which SIL Wheel tool to reach for. **Purpose**: stop the "confidently wrong" failure mode where an agent picks a noisy tool, sorts by `score`, returns 20 clips, and reports them as matches without acknowledging the calibration trade-offs.

## Cardinal rule — be calibrated, not confident

> Every search mode here has different precision/recall trade-offs. None of them are ground truth. **Report your tool choice and your confidence in it explicitly.**

Recurring agent failure modes this doc tries to prevent:

1. Using `caption_search("safety driver overrides")` and reporting "12 matches" — captions are auto-generated by Qwen2.5-7B and frequently wrong. **Real precision can be < 30%** for behavioural / agentive queries.
2. Using `classifier_search(label, threshold=0.5)` and reporting the top 20 — classifier scores are NOT well-calibrated probabilities. `0.5` is high-recall but **30–60% precision** for most labels.
3. Using `trajectory_search_by_clip(seed)` and **sorting descending** by `trajectory_score` — that field is a DISTANCE (lower=better). The SDK now masks this in `best_score`, but the raw field still trips up direct sorts. See `anti-patterns.md § 12`.
4. Compounding two unreliable tools (e.g. caption ∩ classifier) and assuming the intersection is high precision. Errors compound; intersection ≠ guarantee.
5. Reporting "VLM-confirmed precision: 50%" without confidence intervals. `n=100, p=0.50` has 95% CI of `[40%, 60%]`. State this.

## Per-tool calibration table

For each search mode below: what it's **actually** good at, what it's **actually** bad at, observed precision against blind VLM-validation, and when to combine.

### `caption_search` (FTS5 over Qwen2.5-7B captions)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | ~1–5 s on prod, ~5–15 s on dev |
| Recall                  | Mid — only finds clips whose caption literally mentions the query token |
| Precision (concrete objects) | Good (~60–80%) for "fire truck", "construction cone", "rain" |
| Precision (behavioural / agentive) | **Poor (often <30%)** for "ego brakes hard", "safety driver overrides", "back-and-forth lane change" — the captioner is descriptive, not analytic |
| Mode pitfalls           | `mode='all'` (default) is FTS5 AND-of-words; 4+ word natural-language queries return 0 silently. Use `mode='any'`. |
| Composability           | Excellent for narrowing candidate pool. Pair with classifier + VLM-validate. |

**When to use alone**: short, concrete-object queries — "rain", "construction zone", "tunnel", "school bus".

**When NOT to use alone**: behavioural patterns, multi-step temporal scenarios, or anything the captioner wouldn't describe in passing.

**Honest reporting template**: *"Found N clips whose caption mentions '<query>'. Captioner is auto-generated and frequently wrong; precision likely <50% without further validation."*

---

### `caption_search_any` (FTS5 OR-of-terms)

Same calibration as above; just OR'd. Note the silent ~100K cap on total — split your filter if you need more. Useful when you want broad recall and will VLM-validate downstream.

---

### `caption_embedding_search` (Qwen3-Embedding-8B + FAISS)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | ~2–8 s |
| Recall                  | Higher than FTS5 — semantic match, not lexical |
| Precision (concrete)    | Comparable to FTS5 (~60–75%) |
| Precision (behavioural) | Slightly better than FTS5 (~30–45%) — still bottlenecked by the underlying captions, but synonyms / paraphrases work |
| Calibration             | Returns a similarity score 0..1; treat scores >0.5 as relevant. Does NOT calibrate well across different queries. |

**When to use**: paraphrastic queries — "near miss with cyclist" might catch captions that say "almost hit a biker".

---

### `semantic_search_by_text` (Cosmos text-to-video)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency (prod, GPU)     | ~3–5 s |
| Latency (dev, CPU)      | **~120 s** per call — and `search_all_pages` re-runs inference per page. Use `export_search_clip_ids` instead, or stay on prod. |
| Recall                  | Visual concept match — different from caption match |
| Precision               | Mid (~40–60%) for visual concepts; biased toward training distribution of Cosmos |

**When to use**: visual concept search where captions might miss it (e.g. "aerial view of intersection" where caption focuses on cars).

**Trap**: `search_all_pages(semantic_search_text=...)` is forbidden — the SDK raises. Use `export_search_clip_ids`.

---

### `semantic_search_by_clip` (Cosmos clip-to-clip)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | ~2–5 s — pure FAISS lookup |
| Recall (similar visual context) | Excellent |
| Precision (similar **scenario** vs **just-similar-looking**) | Mid-to-high — works because Cosmos was trained for visual+behavioural similarity |
| Calibration             | `semantic_clip_score` is a similarity, higher=better, range typically 0..1 |

**When to use**: dataset expansion from a known-good seed clip. Pair with `expand_clip_set` for iterative growth. **This is the highest-precision-per-minute method for rare scenarios** when you have ≥5 confirmed seeds.

---

### `trajectory_search_by_clip` (kinematic shape similarity)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | ~3–10 s |
| Recall                  | Finds kinematically similar clips (same speed/curvature/braking pattern), regardless of visual scene |
| Precision (same behavior, different scene) | Good |
| Precision (same scenario)| Mid — same trajectory shape can occur in totally different contexts |
| **CALIBRATION TRAP**    | `trajectory_score` is a **distance** (lower = more similar). **Sorting descending puts the LEAST similar first.** SDK now exposes `r.trajectory_distance` (alias) and `r.trajectory_similarity` (1/(1+d), higher=better) and `r.best_score` returns the similarity transform. |

**When to use**: behavioural pattern expansion from a confirmed seed (e.g. "find more clips where the ego does a hard brake at this speed"). **Combine with Cosmos clip-to-clip** to constrain to similar scenes.

**Honest reporting**: *"Top N clips by trajectory shape similarity to seed; visual context may differ."*

---

### `trajectory_predicate_search` (`search_speed=...` expressions)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | **~50–150 s** — this is the slowest single-call mode |
| Recall                  | Exact match on the predicate (high) |
| Precision               | High by construction (it's a hard filter) |
| **DATA SOURCE TRAP**    | Returns 0 silently on MADS-1M, MADS, OpenDV-YouTube, MultiCountry-800K, Physical AI, OGameData, NVIQ. SDK now warns. Use AV V1/V2/V2.2, Waymo, or celsius. |
| Variable vocabulary     | `speed`, `acceleration`, `jerk`, `curvature`, `speed_kph`. Functions: `mean`, `min`, `max`, `sum`, `all`, `any`, `len`, `abs`. **Curvature is unsigned magnitude.** |

**When to use**: behavioural predicates with hard kinematic constraints — "speed exceeded 120 kph", "max curvature > 0.05" (tight turn).

**When NOT to use**: as primary filter on a non-AV source. Use a classifier or caption pre-filter first, then refine via predicate.

---

### `classifier_search` (logistic regression on Cosmos / caption embeddings)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | ~1–3 s |
| Available labels        | 110+ (cosmos: 109, caption: 3) — see `client.list_classifier_names()` |
| **Threshold calibration** | Scores are NOT well-calibrated probabilities. Effective behaviour: |
|                         | - `threshold=0.5` → high recall, **30–60% precision** (typical); use for rare-event mining + downstream validation. |
|                         | - `threshold=0.7` → balanced (~60–80% precision). |
|                         | - `threshold=0.85+` → high precision, low recall. |
| **Coverage trap**       | Inferences are NOT uniform across data sources. `Change lane to the right` returns 1.4M on AV V2 train but **0 on MADS-1M**. Run `client.get_classifier_coverage(label)` before composing. SDK warns on the worst-known cases. |
| **Name resolution trap**| Names are case-sensitive on the server. Use `resolve_classifier_name(query)` — but the v1.8.2 SDK fixes a bug where wrong fuzzy matches were returned (e.g. "change lane to the right" → "fence on the right"). |

**When to use alone**: when the classifier name maps cleanly to your scenario AND the data source has inferences AND you can pick a threshold based on the per-classifier precision/recall trade-off.

**When NOT to use alone**: rare behavioural scenarios with no dedicated classifier; multi-step temporal patterns ("right LC then left LC within 5s"); anything where you're guessing the right threshold.

**Honest reporting template**: *"Filtered by classifier '<name>' at threshold T (precision typically X-Y% at this threshold). N clips returned. Recommend VLM-validate a 100-sample to confirm precision before committing."*

---

### `world_model_search` (perception bbox stats)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | ~1–3 s |
| Filters                 | object class (`PEDESTRIAN_UNKNOWN`, `VEHICLE_CAR`, etc.), min/max count, max distance (m), min duration (s), angle sector |
| Precision               | High (these are detector outputs, not classifier scores) |
| Recall                  | Bounded by detector confidence threshold (server-side) |

**When to use**: object presence questions ("clips with ≥2 pedestrians within 30 m"). Almost always cleaner than caption / classifier.

---

### `annotation_search` (manual + autolabel labels)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | ~1–3 s |
| Coverage                | Sparse — 687+ labels but most have <100 annotations |
| Precision               | High (manual labels), variable (autolabels — check `label_types='manual'` to be strict) |

**When to use**: when there's a relevant manual label (check `client.get_annotations_summary()` first). 19 manual annotations are useful seeds for `expand_clip_set`.

**Trap**: visibility depends on `project_source`. The default `project_source='Alpamayo'` may hide annotations in other projects. Pass `project_source=None` to search across all visible projects.

---

### `vlm_judge_validate_search` (Gemini 3 Flash judgment)

| Aspect                  | Reality |
|-------------------------|---------|
| Latency                 | ~30 s per chunk of 30 clips (now auto-chunked) |
| Recall (when shown a true match) | Mid-to-high (~70–85%) |
| Precision (when says match) | Mid-to-high (~70–85%) |
| **Stochasticity**       | **Non-deterministic.** Re-running the same query on the same clips can flip ~10–15% of decisions. For high-stakes work, do a 3-run consensus (`match` if ≥2/3 agree). |
| Bias                    | Confirmation bias toward the query phrasing — careful with leading questions like "is this a back-and-forth lane change?" (will over-call) |

**When to use**: as the **final precision filter** after broad mining via caption/classifier/expand. Don't use as primary search (too slow per clip).

**Practical limit**: ~1000 clips per session. For >1000 candidates, train a custom classifier on the dev server instead.

## Composition rules — when to stack tools

| Scenario | Recommended stack |
|----------|-------------------|
| Concrete object + scene ("rainy night highway")        | `caption_search('rain night highway', mode='any')` ∩ `classifier_search('Rain', t=0.7)`. Optional VLM-validate sample. |
| Behavioural pattern with classifier                    | `classifier_search(label, threshold=0.5)` → VLM-validate 100-sample to estimate precision → set threshold accordingly. |
| Behavioural pattern WITHOUT good classifier            | **Seed → expand → validate**: VLM-validate 50 caption results → use confirmed positives as `expand_clip_set` seeds → optional second VLM pass. |
| Multi-step temporal pattern                            | DO NOT compose classifiers — the temporal sequence isn't expressible. Use seed→expand→validate pattern with VLM. |
| Edge-case mining (rare event)                          | `classifier_search(label, threshold=0.5)` (high recall) → `expand_clip_set` from confirmed positives → `score_clips` for downstream weighting. |
| 3D-loop / closed trajectory                            | `caption_search` for "roundabout / loop / parking lot / donut" + `semantic_search_by_clip` from a known seed → analyze trajectory positions client-side for `start↔end` distance. **Note**: MADS-1M's 10 s clips can't fit a true 360° loop; AV V1/V2's 20 s ones can. |

## Anti-patterns to avoid (concrete)

1. **"caption_search returned X, therefore X clips match"** — wrong. Caption search returned X clips whose caption *mentions* the query. Validate.
2. **"classifier_search at threshold 0.5 returned 12,000 — that's the answer"** — wrong. At 0.5 you have 12K candidates with maybe 30-60% precision. The answer is "12K candidates; sample-validate to estimate precision".
3. **"trajectory_search_by_clip returned the most-similar clips — the top 20 are best"** — wrong. The raw `trajectory_score` is a distance; sorting descending gets the LEAST similar. Sort by `trajectory_similarity` ascending or use `best_score` (now fixed to handle this).
4. **"VLM Judge said yes, so it's a true match"** — wrong. VLM Judge is ~70-85% accurate AND non-deterministic. For customer-facing claims, do a 3-run consensus.
5. **"I composed five filters and the intersection is 32 clips — these must be all matches"** — wrong. Each filter has its own precision/recall. Intersection helps but doesn't guarantee. Sample-validate.
6. **"I tried caption_search and got 0; therefore there are no clips"** — wrong. Try `mode='any'` / `caption_search_any` / `caption_embedding_search` / `semantic_search_by_text` / `classifier_search` / `expand_clip_set` from any one example. The most common cause of "0 results" is wrong tool, not missing data.

## Honest reporting templates

When delivering search results to a teammate or downstream system:

```
Tool: <tool name and parameters>
Source: <data_source>
Total candidates: N
Reported precision (estimated):
  - <basis: VLM-validated 100-sample, n=100, p=0.X, 95% CI [low, high]>
  - <or basis: classifier @ threshold T, expected precision X-Y% based on calibration table>
Caveats:
  - <e.g. "captions are auto-generated, sample-inspect 5 before committing">
  - <e.g. "VLM Judge non-deterministic; results may shift ~10-15% on re-run">
Suggested next step: <e.g. "VLM-validate 100 random samples to confirm">
```
